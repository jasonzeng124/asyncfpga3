# C-pipe: gcd_hw under a pipelined environment -- counterexample

## Problem, plainly
THE goal (PROGRAM.md, owner 2026-10-31) asks for: for every sequence of pairs offered on the
input channel, where the environment may offer pair k+1 as soon as the input handshake of pair
k completes, the k-th output is gcd of the k-th pair, and every pair is answered.

**This is false for gcd_hw's handshake network**, in two ways, found by simulation:
1. **Reordering.** A later pair that skips the first loop overtakes an earlier pair that
   iterates in it. The k-th output is then the gcd of a different pair.
2. **Deadlock** (finite storage). Two threads in the loops block each other at the loop-header
   muxes and arbitrated merges. No output is produced at all.

## What this does NOT show yet
- Unit delays are ONE delay assignment, not the prjxray band. The reordering for (2^20,2^20),
  (3,5) has a wide margin (pair 2 out at 603 ticks vs pair 1 at 1291: 20 extra loop
  iterations), so it should survive any band; that is argued, not proved.
- CapstoneNet is the network built from bdc's graph and link plan, not the bitstream.
- The gcd_rig.v comment "the kernel acknowledges start only when it is finished" disagrees
  with this model (pair 1's input handshake completes at tick ~140, out0 at 430 for (12,18)).
  Which is right should be checked in research's routed GLS.

## Why
- **Reorder.** The loop-header control_merges are arbitrated merges (bd_arbiter). A pair that needs fewer loop
  iterations (vector 4: none) passes the merges while the earlier pair is still circulating, and leaves first.
  The data stays consistent per pair (each mux is steered by its own merge's index token), so the values are
  right and only the order is wrong (token level: 300 random runs, multiset always right).
- **Deadlock.** Vector 9 twice: in the deadlocked state (CapNet, unit delay) both pairs' tokens sit in the first
  loop (the "both even: shift" loop; pending values 32768/16384 and 2048/1024 are both pairs' halvings). bdc gives
  each loop the minimum 3 storage stages, enough for ONE token; C's own `Ring.k_tokens` (C-9) says a ring with k
  tokens needs 2k + 1 stages. Two invocations in one loop is two tokens in a ring sized for one.

and in one of them the first result delivered is the second pair's.

### Where the target route wedges (vector 9 twice, `-DPROBE`, cells/gls gen_probe.py last-transition dump)
Pair 2's in_ack rises at 851.9 ns and never falls (its return-to-zero never completes; in the Lean PipeDead run it
is likewise start's acknowledge that stays high). The last transitions in the whole design (882-891 ns) are in
`umux0`, `umux1`, `umux2` and `ulink_n32__2`: mux0-2 are the header muxes of the first loop (control_merge2; GcdHw
rules 34-36), the same loop the CapNet deadlock sits in. Nothing moves after 891 ns (run to 101 us).

## What restriction would be enough? (token level, simulation only)
`tools/pipe/seqtok.py`: 400 random sequences of 2-3 rig vectors, pair k+1 offered as soon as out0 holds k results
(in 103 of the offers pair k still had tokens in flight, e.g. on their way to sinks): every result right and in order.
So "offer pair k+1 only after out0's k-th result" looks sufficient at the token level; at the handshake level the
capstone's `gcd_rig_all` (C-8s3) already proves safety (every out0 offer = gcd) for gcd_rig's sequential env under the
cell models; liveness there still rests on H_NO_DEADLOCK''. Not proved for a general sequential env.

Acceptance gate for the target GLS (cells/gls tb_gate.v on the same generated netlist, iverilog 12's SDF annotator):
`ANNOTATE_DONE`, 0 `SDF WARNING`/`SDF ERROR` lines, rc 0. Sequential controls 9/9 and 2/4: both results, correct.
