benchcap (subagent gcdclean, 2026-11-19): why isprime / gcd never end CLEAN in auto_size.sh, and CA_BENCHCAP=1

QUESTION.  On every iteration of the automatic sizing loop (auto_size.sh: corner_audit CA_SIZERULE=1 CA_JOINAWARE=1,
corners 0.20 / 0.31) one rule-A' row on isprime and on gcd is "unfixable": isprime umux13 -5125 / -5612 ps, gcd umux21
-3422 / -3680 ps, each with a "j" row "joined: not applied, keeps A': its data reaches N input(s) that are not a latch's
data or a select".  Hypothesis to test: the late data goes to flip-flops of the PS-clocked bench, which samples only after
a synchroniser has seen the request, so the row is false.

2. THE A' ROW IS A LAP THROUGH THE BENCH'S ACKNOWLEDGE (same files, "upstream links" section)
  isprime 0.20, from ulink_n_trueResult_62 stage[1]'s C node: req at umux13's tail 1923 ps (1 crossing); "data" =
  the decode LUT sel[0] at 6843 ps, 2 crossings deep, by
     C node > uj3 > |j LUT > uor > udly (1 link) > bench LUT $23671 (o_ack_pl = (bench_busy ? bench_o_ack : ctrl_o_ack)

  i.e. the select link's return to zero after the bench has acknowledged out0: the next phase of the handshake, not this
  token's data.  The timing graph holds no flip-flop state, so it crosses the AND gate from core_o_req as if the clocked
  bench_o_ack were already 1; on silicon o_ack_pl rises only after bench_o_ack, which the bench sets on the capture
  edge.  The lap runs through umux13's own delay line on both sides (request and "data"), so removing or padding that
  line moves neither margin: corner_audit finds no line with sensitivity -> "unfixable".  gcd umux21 is the same path

3. THE BENCH'S CAPTURE (cells/hw/gen_bench.py)
  out0_req = o_req_pl -> (a) o_req_latched (async-set flop, yosys dfflegalize emulation) -> sync_o_reql[1:0];
                         (b) sync_o_req[1:0]; both 2-flop synchronisers on aclk (fclk0_bufg).
  S_WAIT_RES: if (o_req_l_s && (o_req_s || res_wait == 8'hFF)) { result_hold <= o_data_pl; bench_o_ack <= 1; }
  o_req_l_s = sync_o_reql[1], o_req_s = sync_o_req[1].  For both to read 1 before edge E, each first stage must have
  sampled 1 at an edge <= E - 2T, and it can only sample the request if the request reached its D before that edge plus
  its hold window: E >= t_r + 2T - (window).  o_data_capture samples every edge but is read only through ODATA while
  hold_valid = 0 (the host's manual handshake, ms after an idle bus).  The data cannot change before E: the mux's inputs
  are released only through z_ack = o_ack_pl, which needs bench_o_ack, set ON E.
  Clock: FCLK0 = 100 MHz in every xsdb script found (xsdb_bench_gen.tcl default CLK_CTRL 0x00100A00); build_bench.sh
  closes the bench at 83 MHz ("the PS drives them at CLK_CTRL=0x00100C00, which is 83.3 MHz").  Fastest: T = 10 ns.
  -> the bench samples out0's data >= 2 x 10000 - 1000 = 19000 ps after out0_req first reaches a synchroniser's first
  stage (1000 ps: first stage's setup/hold window + the capture flop's setup + BUFG skew; an allowance, not measured).
  Measured (the A'j rows, worst launch; entry = the request's earliest arrival at a flop on fclk0_bufg):
      route / corner          data at result_hold D   request entry   data - entry   A'j margin (event = entry + 19000)

DECISION: the row is false (a lap), and the constraint it stands for (out0's data at the bench's flops) is met by the
synchroniser with ~18.6 ns.  The hypothesis is right for the 2 (gcd: 64) flop sinks; the other 4 (gcd: 3) sinks are the
mux's own select decode feeding its own join, i.e. its request path, not data.

4. THE CHANGE: corner_audit.py CA_BENCHCAP=1 (opt-in, with CA_JOINAWARE=1; header comment there), A'j only:
  * a D / CE pin of a flip-flop on a BUFG clock is a "clocked" capture; event = the earliest arrival (A'j's early walk
    from the launch, through the operator's tail) at any input pin of a flop on that clock reachable from the operator's
    request tail without crossing storage, + CA_BENCHCAP_PS (default 19000); data leg guarded as A'.  A request that
    reaches no flop on that clock leaves the sink odd.
  * an input of one of the operator's own join C-elements (a storage node inside the operator that reaches its request
    chain head without crossing storage) is neither capture nor odd (CA_BENCHCAP_OWNJOIN=0: odd, as before).
  Unset: no code path changes (clk_of empty, both new branches guarded by BENCHCAP, the row text gets "").
  CA_FAST=1 (auto_size.sh's default) stays exact with it set: ca_fast_check.py on xorshift s1 it4 at 0.20, base + 48
  lines (UMUX3 among them) + 2 verify-like specs, each run both ways and compared whole: 0 of 51 differ
  (fastcheck_xorshift.txt).  The memo key of A' / A'j sites carries CA_BENCHCAP / _PS / _OWNJOIN.

WHAT THIS DOES NOT SHOW
  * No board run and no GLS: the 19000 ps rests on reading gen_bench.py (2-flop synchronisers in front of the only
    request-correlated capture) and on FCLK0 <= 100 MHz in the board scripts; the 1000 ps allowance is not measured.
  * o_data_capture is not request-gated at all; checking it against the same event is vacuous (it is read only on the
    host's manual path).  A bench that sampled out0's data outside the 4-phase window (the old S_NEXT read of
    o_data_capture, a real board bug) would not be caught by this rule: it checks setup to the capture, not that the
    capture is inside the window.
  * One route per kernel and one seed (the rule is deterministic per route); the conclusion does not hinge on the
    route: the A'j margins are 17.4..18.7 ns on 5 kernels, ~40x the route-to-route scatter of a few hundred ps.
  * The A' row stays in the report as 'a' (reported, not sized) and still reads -5125: rule_a_from_link's "one crossing
    more for the data" allowance lets a lap through a combinational acknowledge count; not changed here.
  * bdc_muxnN's own select race (s settling before ctl_req at the decode LUTs) is measured by NO rule, before or after
    this change: select_consumers() reads uj0/uj1 as a library bd_mux's join (I1 ctl_req, I2 s), but in bd_c2 I1 is b
    (= sel[k]) and I2 the feedback q.  The line that protects it (isprime: BD_SZ_..._ULINK_N_INDEX_71, the select
    link's rdly, 3 links) is "on no measured constraint: kept" -- kept at its start size (estimate 8 x 0.3 -> 3, it 0..6).  At 0.20 on
    isprime it 5 s leads ctl_req at the decode LUTs by 363..633 ps unguarded (isprime_s1_it5_umux13_selrace.txt).
