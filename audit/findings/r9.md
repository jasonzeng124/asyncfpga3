## Floating-pip / unused-LUT check (coordinator's request)

**(a) The 73b08ca decoder.**
- Seed 4: 0 "pip driven from a floating node", and the equivalence check is EQUIVALENT.
- Seed 5: 8 floating pips, and the check is NOT EQUIVALENT. Two `$PACKER_GND_NET$LUT$*` LUT1 buffers differ (SLICE_X24Y37/B6LUT and SLICE_X26Y32/B6LUT), because their A1 is 1 on the bits side and 0 in the JSON. SLICE_X28Y33/A has one more pin with the wrong constant; it is harmless because the LUT does not read it.
- This agrees with research's "8 on seed 5, 0 on ... 4" (JOURNAL 03:53).
- The seed 5 rows above were therefore simulated on a netlist that is NOT EQUIVALENT to the JSON. Research applied the same "stop sign" to its own row.

**(b) The wt-r10 decoder.**
- Seed 4: the decode is byte-identical at both corners.
- Seed 5: the check is EQUIVALENT. `sink roots` gains `const/unused-lut: 3`. netlist.v differs from the old decode in exactly 3 lines: `ICBUF ic_027199 / ic_029729 / ic_032483`, with `.I(n3)` (PSEUDO_VCC) becoming `.I(n2)` (PSEUDO_GND). These feed SLICE_X24Y37/B6LUT A1, SLICE_X26Y32/B6LUT A1 and SLICE_X28Y33/A6LUT A3.

**Independent judgement: is "an unconfigured LUT's O6 resolves to constant 0" right? Yes, for these sinks.**
- *Routed JSON intent* (`r9/float/trace_json.py`, `float/s5_json_trace.txt`): all three sinks are on `$PACKER_GND_NET`. The path upstream is `INT_L_X0Y33/GND_WIRE -> SITEWIRE/SLICE_X22Y33/A -> CLBLL_L_X16Y33/CLBLL_LL_A -> INT_L_X16Y33/LOGIC_OUTS_L12 -> EE2BEG0/NE6BEG0 -> ... -> IMUX15 / IMUX_L1`, ending at SITEWIRE SLICE_X26Y32/B1, SLICE_X28Y33/A5 and SLICE_X24Y37/B1. nextpnr intends GND, sourced from the A output of slice X22Y33, and the JSON places no cell on SLICE_X22Y33.
- *Bits*: board.fasm has **no feature at all** for tile CLBLL_L_X16Y33, so every INIT bit of that slice's LUTs is 0. The interconnect pips on the path are present as bits: `INT_L_X16Y33.EE2BEG0.LOGIC_OUTS_L12`, `NE6BEG0.LOGIC_OUTS_L12`, `INT_L_X18Y33.EE2BEG0.EE2END0`, `INT_L_X20Y33.IMUX_L1.EE2END0`, `INT_R_X19Y32.IMUX15.EL1END3` and `INT_R_X17Y37.IMUX15.NW2END_S0_0`. The CLBLL_LL_A -> LOGIC_OUTS12 hop is an always-on ppip with no bits.
- A 7-series LUT output is INIT[address]. With INIT all zero, O6 = 0 whatever the inputs are, including floating ones. The A site pin is O6 with no configurable mux. So the source is a real constant 0. The old fallback, the IMUX's VCC default, is wrong, because the IMUX has an explicit pip selected and reads that wire.
- The new rule's scope in the code is narrow: SLICE_LUTX, INIT == 0, name ending in `6LUT`. It gives 0 only where the bits really have no INIT. It changes nothing on seed 4. Research reports that seed d decodes md5-identically under the new rule; I did not re-check that.
- *Consequence*: the two GND LUT1 buffers feed F7AMUX data input 0 of two `urig.udut.ushrsi2` cells (SLICE_X24Y37/F7AMUX and SLICE_X26Y32/F7AMUX). Under the old decoder those inputs read 1 instead of 0. On these 16 vectors the difference is not observable: the logs are byte-identical. So seed 5's old PASS was right by luck of coverage, not by construction.
