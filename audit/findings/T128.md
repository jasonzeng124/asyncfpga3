# T128: own static bundling check (rule A style) for fused ops; item 31 (uselect0 16 -> 7, uaddi0 12 -> 9) vs item 28

Tool: audit/t128/bundle.py. It runs on the baked netlist of an own GLS corner (own graph t93/sta_lib, own latch mapping as t109/rule_h.py).
For each upstream link U and each bit b of the downstream latch:
* data_max = LONGEST path from U's enable node, through U's latch (en->O), through the combinational cone (stopping at every other state node), to b's D pin, plus D->O.
* req_min = SHORTEST OR-join path from U's enable node to b's enable pin, plus en->O.
* slack = req_min - data_max.

On the request side, the gate input of each delay-chain element g[k] with k >= 1 is excluded:
* bd_delay_gated sets g[k] = s[k] & gate, so a RISING request must ripple through s[k]. The gate is a fast-FALL path.
* The first version did not exclude it. It reported uaddi0 at -99..-984 ps on item 28, a board-CONFIRMED route, which is a model error.
* With the exclusion, 147 / 135 chain elements are handled.

The OR-join request bound is a lower bound on the real request (the joins are C-elements), so a positive slack is sufficient. It need not be tight to the line length: the earliest request can come through the steer join's other input.

* /root/t65/cs3aneg_20 is item 31's route with +3000 ps on the 4 INTERCONNECT arcs ulink_n11.lat.odd.u/O6 -> uselect0.* (own t125/inject.py).
* bundle.py on its FAST_MIN bake gives **-1441 ps** (= +1559 - 3000) and names **ulink_n11 -> pair[6]**. The tool ranks the broken build below the good one and names the failing link.
* GLS of the +3000 injected build at FAST_MIN: **PASS 13/13** (no hang). The static check is stricter than the gate here: the real request is later than the OR-join lower bound, through the C-element joins and the steer join's other input.
* So this control shows the tool flags the injected build. It does not yet show the tool catching a build that actually fails.
* +10000 control (t128/neg2.sh): static **-8441 ps**, and the gate still PASSES 13/13 at FAST_MIN.
  * The 1-bit e0 operand (ulink_n11) evidently rarely or never changes while a request is pending on these vectors (cf. T125).
  * A delay on it is not exercised.
* Third control (t128/neg3.sh): +3000 ps on the 17 arcs from ulink_n10__3's latches (e2, the 32-bit n>>1 operand) into uselect0.
  * Static **-917 ps**; the gate still **PASSES 13/13**.
  * The OR-join request bound is loose here: it takes the earlier of the steer join ucond_br7's two inputs (n31__0, not uselect0's delay line), while the real request waits for both.
  * So the tool ranks the injected builds below the good one, but it is pessimistic by more than 3 ns on this path.

  * Static **-9917 ps**, naming ulink_n10__3 as the binding link.
  * **The tool flags a build that actually fails**, and ranks it below the good build (+1559) and below the milder injections (-917, -1441, -8441), which the gate still passes.
* Summary of the controls: the static check is never looser than the gate in these 4 runs. It is pessimistic by more than 3 ns on the uselect0 path, because the OR-join request bound takes the earlier input of the steer join.
