## Why research's check reports a violation (auditor, from research's code and a diagnostic run)
- RTL (`l5_1/xorshift_kernel_bench.v`:683-688): `ucond_br6`'s request is `bd_join #(.N(2)) ucond_br6_j` of
  `{n32__3_req, n30__0_req}`; `n32__3` is the compare result's fork output (after ucmpi1's matched delay), and s =
  `n32__3_data` = ucmpi1's output. `bd_join` = `bd_ctree` = `bd_c2`, a Muller C-element (cells/rtl/bd_ce.v, bd_ctl.v): the
  request cannot rise before the compare's own request.
- research `cells/verify/skew.py` walk(): when the request walk crosses a storage node it seeds it with
  `better(v, seeds[o])` over the node's inputs -- on the shortest (request) leg, the EARLIEST input. For the join C-element
  that is OR semantics.
- Research's own tool, run by the auditor on the route's nextpnr SDF (diagnosis only; `t93/research_skew_l5_1.txt`): req
  "earliest 4581 ps, 1 storage crossing(s)", sel 9232, "-4651 ps raw" -- research's numbers exactly. The kernel's sizes are
  uaddi0 6 and ucmpi1 9 delay elements (~419 ps each by skew.py's own figure): a request that waits for the compare needs
  >= ~6.3 ns on that chain alone, so the 4581 ps request path reaches the join through n30__0 only (uaddi0's chain), i.e.
  it fires the C-element on its first input. The own OR-join diagnostic (-3087 at the worst corner, unguarded) is within
  ~0.1 ns of research's corner_audit -3.2 ns.

## Verdict
- "-3.2 ns at the worst corner": **REFUTED as a violation** -- a check artifact (C-element join modelled as OR on the
  request leg). With the join modelled, rule E holds at ucond_br6 for a full 32-bit carry: +1.59 ns at the worst corner
  (unguarded); with research's guard constants on the full legs (0.97 x req, 1.03 x sel) about +1.13 ns.
- "-4.65 ns raw at nominal nextpnr SDF": the number reproduces with research's tool, but it is the same artifact. With the
  join modelled on nextpnr's SDF the auditor has no own number; a rough estimate (4581 + ~3770 ps of ucmpi1 chain vs 9232)
  is still about -0.9 ns, so on nextpnr's SDF the question is **UNVERIFIED** (research itself no longer uses plain nextpnr
  as the gate, 1827c16b..e4289af2).
- Consequence: item 18's hold rests on a mis-modelled join at the calibrated corners. The same skew.py walk is used for
  every steer and mux select site (rule E) and inside corner_audit's sizing, so other rule-E verdicts and sizes that pass
  through a join C-element on the request leg are pessimistic in the same way (sizes larger than needed, false holds); none
  is shown unsafe by this.
- Limits: simulator delay model, not silicon; hold half of rule E (s stable while req high) not checked statically (the T91
  monitors saw 0 violations dynamically); launch latch input assumed set up; overlapping n7 / n11__1 launches not modelled.
