# T9: SpecRunt's H_RUNT(w) vs the owner's decision 2 (formal 65323d29; owner commit 94b7fd79)

Owner, decision 2 (formal/PROGRAM.md): "**H_RUNT(w) is a sixth allowed hypothesis:** a LUT input pulse narrower than
w ps does not propagate to its output. Use `SpecRunt.lean` (`NetCorrectSeqRunt w`). ... w = 20 ps as the headline".

## What SpecRunt.lean says (read at 65323d29, built in my clean tree)
`GateOKRunt w p c g x` = `GateOK` plus, for EVERY gate `g` of the net and every pin, `NoRuntRead w (x in) (f i t)`:
no read time lands in a pulse narrower than `w`. `BehavesRunt` requires it of every gate in `N.gates` (lines 35-44).
The gates of `Decoded.net` include all routing: 167,588 pips (70,528 of them pseudo pips with arc ⟨0,0,0,0⟩) and
10,548 site hops (all ⟨0,0,0,0⟩), not only LUTs.

## Finding: DEVIATES (stronger than the owner's hypothesis; hides output glitches narrower than w)
1. **A zero-delay gate cannot skip a pulse.** For arc ⟨0,0,0,0⟩, `Adm` forces read delay 0 (upper end
   (1+κ)·lerp(0,0,c)·g = 0), and `Gate.start` = 0. So `GateOKRunt w` for such a gate is not a filter: it says the
   gate's INPUT NODE never carries a pulse narrower than `w`, from time 0. Proved in Lean, my own file
   `audit/lean/T9/ZeroPinRunt.lean` (compiled against formal 65323d29; axioms propext, Classical.choice, Quot.sound):
   `zero_pin_bans_runt`, `behavesRunt_bans` (any gate of the net with a zero arc on pin 0 and start <= a: no
   `Pulse` of width < w on its input at a), `start_zero` (start = 0 for arcs = [⟨0,0,0,0⟩]).
2. **On the target this covers the kernel's handshake outputs.** `audit/t9/zero_readers.py` on my own decode
   (= Decoded.net, 0 differences, T4/T7): out0_req, a_ack, b_ack, start_ack and pend_ack are each read by exactly
   one gate, a site hop with arc ⟨0,0,0,0⟩, which stays in `circuit N B` (its output is not an env node).
   9,984 of the 12,856 read LUT/MUXF/CARRY outputs are read by a zero-delay pin.
3. **Consequence.** `BehavesRunt w` therefore ASSUMES that no LUT output read through a zero-delay hop (all kernel
   handshake outputs among them) ever has a pulse narrower than `w`, including hazard glitches made by the LUT
   itself from two input edges close together. `Correct` checks the outputs with `ReqMoves`/`AckMoves` (Spec 263-271:
   out0_req may fall only while out0_ack is high), so a glitch on out0_req narrower than `w` is a protocol violation
   that `NetCorrectSeqRunt w` can never report. At the headline w = 20 that is the very failure class my fid GLS
   showed at B's ua1 delays (T6 row 8: out0_req 5-15 ps pulse trains with the default resolver).
4. **The owner's wording is weaker:** "a LUT INPUT pulse ... does not propagate to its output" restricts what a LUT
   does with a narrow input pulse; it says nothing about route gates and does not forbid a LUT from emitting a
   narrow hazard pulse. A version matching it would put `NoRuntRead` only on LUT pins (lut6/lut5, perhaps
   muxf/carry), and leave pips/hops as plain `GateOK`.
5. Not shown: that NetCorrectSeqRunt w is vacuous for some legal environment (that would need every behaviour of
   that environment to contain a narrow pulse on a zero-delay-read node); only that it is blind to sub-w glitches on
   those nodes. The pessimistic statement NetCorrectSeq (w = 0) is unaffected (`noRunt_zero`).

## Also: A's H_RUNT simulation points (af137976, hrunt_sweep.txt): UNVERIFIED, and a wording correction
- A's journal says "every pin skipping pulses narrower than w"; simb.py's `--gfilter W,T1` (lines 173-180) filters
  only pins whose window start AND delay are >= W, and only pulses already ended at the read (`fval`). Zero-delay
  pins (half the net's pins) never filter. So the simulated behaviours are neither the Spec's H_RUNT(w) (stronger,
  above) nor the owner's; a simulated CHAOS at κ = 0.20 is not shown to be a behaviour admitted by
  `BehavesRunt 20` (it may contain sub-20 ps pulses on zero-delay-read nodes, which BehavesRunt excludes).
- "simb's window still clips to the pre-change band; at corner 0.5 and g = 1 that does not bind": true for the ua1
  adversary's own arcs (all fmax/smax, fmin/smin <= 0.42), but not in general: on my decode at c = 0.5, g = 1 the new
  window leaves the old band on 26 arcs upper / 14 lower at κ = 0.20 and 251 / 14 at κ = 0.25 (BRKH *_SLOW widened
  records, GFAN pips). Harmless for these runs only if no such arc sits at a window end.
- I did not re-run the sweep.
