# T121: Spec.Env is unsatisfiable on partial-ack deadlocks (formal C 3085bc4e9)

Claim (formal C, JOURNAL-C at 3085bc4e9, "finding for A"): with a, b and start sharing one
request node, a run where the kernel acknowledges a and b but never start goes quiet with req
high. No continuation then satisfies Env, so NetCorrectSeq holds vacuously for those delays.

Check (own, independent of C's envcheck):
* Spec.lean:265-277 at formal 103cc6c3c defines ReqMoves and ReqLive. Spec.lean:296-298
  conjoins them per input channel in EnvIn, and Env takes EnvIn for a, b and start.
  Spec.lean:392-394 says B.a.req = B.b.req = B.start.req. All of this was read by me.
* audit/lean/T121/EnvVacuous.lean restates the two definitions and proves `env_vacuous`.
  Suppose r is high at t ≥ R, a's ack stays high from t on, and start's ack stays low from t
  on. Then ReqMoves(r, start_ack) and ReqLive(r, a_ack) cannot both hold.
* Checked with my own Lean 4.35.0, rc 0; the only axioms are propext and Quot.sound.
* I dropped ReqLive's `more` argument because the proof uses only the `r t = true` branch.

Verdict: CONFIRMED, as a statement-level gap.
* Env forbids, rather than refutes, every behaviour in which the circuit deadlocks with only
  some of the shared-request channels acknowledged.
* The liveness part of Correct (AckLive on start, ReqLive on out0/end) therefore cannot catch
  this class of hang. A design that hangs this way satisfies NetCorrectSeq for those delays.
* This is the same kind of gap as the residual-vacuity row for T < D, but it applies at any T.
