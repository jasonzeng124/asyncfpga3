# T130: dynamic rule M at the mux (z_data vs z_req, state A) on items 28 / 31 / 30

Tool: audit/t130/mon_zdata.py (own). It is a PS_MON_GEN hook. For every bd_mux:
* a token starts at each z_req rise (at its driver);
* any change of a data-LUT OUTPUT while z_req = 1 and z_ack != 1 (request pending, not yet acknowledged) is "late".

v1 had no z_ack condition and counted legitimate state-B changes; it is superseded. The z_ack mapping is verified: collatz umux0.z_ack = n9_ack = ufork3's top C-element.

Trace variant t130/mon_zdata_trace.py prints, for each early late change, the LUT input that moved last.

Trace on item 28:
* The late output changes are umux0's z_data bits 12 and 14 (n10__0_data[12] / [14]), 167 ps and 101 ps after z_req.
* The input that moved last is the **y DATA input** n_falseResult_9_data[12] / [14]: the stage-1 output of ulink_n_falseResult_9 (a bd_pipe), whose y_req is one of umux0's join inputs.
* So it is not the select: the selected operand itself is still changing when the mux's request has risen.
* This is the "link D-stable contract" research describes (f4b094782): the falseResult_9 link's Q follows a late D through its transparent latch.
