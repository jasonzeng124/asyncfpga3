## CORRECTION (21:58) -- the mux-monitor counts were per pin, and z_ack was not consulted
t83/mon_mux.py increments its counter once per select PIN (32 data-mux LUTs per mux). umux0's 960 (FAST_MIN / worst) and 672
(SLOW_MAX) are ~30 / ~21 select transitions; 132 on the select-flip vector is ~4. The text above ("960 of ~1460 rises",
"most iterations") was wrong, and the owner's correction note in research/PROGRAM.md (b0f9dafa) quotes it. Also, the
monitor flags a change while z_req is high regardless of z_ack; in 4-phase bundled data the select (data) may change once
every consumer has acknowledged, so a flagged event is a hazard only with z_ack = 0. Research's select_arrival.py
(af6b668a) reports 0 violations on the same route and 10 select changes in its dump. T116b (t116/mon_sel.py) classifies
each transition by (z_req, z_ack); the conclusion "the hold checks are blind to this race" stands only if class A
(z_req = 1, z_ack = 0) events exist.

## T116b / T116c -- resolved (per-event, with z_ack and lateness; t116/mon_sel.py)
colsel0_24, umux0, own oracle 13/13 at FAST_MIN and worst. 48 select transitions per run (counted once each):
- every one STARTS with z_req = 0 (none under a standing request; z_ack therefore irrelevant: classes A and B are 0);
- **24 of the 48 are still arriving at the mux's data-LUT select pins AFTER z_req has risen: 960 pin changes, up to
  487 ps (FAST_MIN) / 579 ps (worst) after the rise.** The select's fan-out to 32 LUTs is spread, and the request rises
  in the middle of it.
So the race is the ARRIVAL race at the mux pins (the request rises before the select has reached every data LUT) -- rule
E's quantity, which research's corrected static summary reports at -87..-255 ps here -- and it occurs on 24 transitions
per 13-vector run, not on "960 of ~1460 rises" (that count was per pin). It violates the owner's arrival criterion as
written in b0f9dafa ("in simulation, the select must not change while the cell's output request is high", read at the
cell's pins). The gate passes because the downstream links' own matched delays absorb ~0.5 ns here.
Research's select_arrival.py reports 0 on this route; if it reads the select at its DRIVER, it misses this by construction
(the driver changes before the rise; the pins after). That matters for item 28, whose open check is exactly this.
