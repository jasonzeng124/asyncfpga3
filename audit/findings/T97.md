## Mechanism (edge trace, `t97/trace3.sh`, `t97/xf2_1_trace3_fastmin.log`; run 2, iteration 2, times in ps)
| t | event |
|---|---|
| 2,064,470 | adder output n29 = 2 settled (bit 1 = 1) |
| 2,071,939 | `n_trueResult_6_u_req` rises: the loop-back pipe's stage 0 opens; dat[33] (stage-0 bit 1) = 1 at 2,072,448 |
| 2,073,699 / 2,074,144 | pipe output request rises; output bit 1 = 1 |
| 2,074,605 | counter link `ulink_n7` (transparent) passes 2: n7_data[1] = 1 (glitches 0/1 to 2,075,150) |
| 2,075,312 - 2,075,944 | **the adder recomputes from the new counter value** (combinational): n29 bits 1/2 toggle (carry glitches) |
| 2,075,813 - 2,076,658 | **those changes pass through the still-open stage 0** (dat[34] -> 1, dat[33] toggles) **and stage 1** (output bit 2 -> 1 at 2,076,707) |
| 2,076,149 | only now does stage 0's request fall (the latch closes) |
| 2,078,972 | counter takes bit 2 = 1 -> **6**; next i+1 = **7** (2,082,567) >= rounds 5: early exit |

The counter ring (`ulink_n7` -> uaddi0 -> trueResult_6 pipe stage 0 -> stage 1 -> umux -> ulink_n7) is transparent end to end
for ~1.5 ns: the counter's next value reaches the loop-back pipe before its latches close. This is a **race-through (hold)
failure** of the counter loop at FAST_MIN on this route. It is not a setup/bundling miss of the kind the static rules A/E
check, and not the umux2 rule-A miss (research's SDF experiment already ruled that out). Research's round-2 sizes changed
the pipe's SDELAY (1 -> 2) and several UACKs, and the route changed with them. Which change opened the window is not
established here.

## Research's explanation at db935e60 vs the own trace
Research (09:13): "every wrong answer equals the PREVIOUS vector's rounds ... the loop compares against the last
transaction's rounds. So the rounds ring's entry (umux2 / its select / the value it latches) takes the stale loop-back token
instead of the new rounds". On the own failing vector (seed 4a56b27b, rounds 5, both runs the same vector), the compare's
rounds operand `n11__1` reads **5 on every iteration of both runs** (trace2), so a stale-rounds token cannot explain this
failure. What the own trace shows is the counter's loop-back pipe racing (above): the stale value there is the previous run's
last i+1 (4). Research's observation on its own vector order may be real, but the locus it proposes (umux2 / the rounds ring)
is **not** what happens in the own failing case. Research's trace is still in progress; the audit will compare when it lands.

## Research's trace (00582e6b, 09:34)
Research withdrew the stale-rounds hypothesis ("rounds is right at the compare (4 throughout); the COUNTER is wrong") and
traced the same mechanism as the audit: ulink_n_trueResult_6 (the counter's loop-back pipe, fed by the adder through fork
branch n30__0 and steer ucond_br6, with no link stage) stays open while the adder's next result arrives; the loop-back i
becomes 6 (or 4) and the loop exits one iteration early. Its point that the static rules do not audit this hold path
(sender is a compute unit, not a link stage) matches the audit's reading. **Mechanism CONFIRMED by two independent traces.**
