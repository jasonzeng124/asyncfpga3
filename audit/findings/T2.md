Owner priority: "any counterexample trace: replay it yourself in the fid GLS". Shard C (d625dab8, notes/C-pipe-cex.md)
reported, from untrusted simulators, that gcd_hw reorders (and can deadlock) when pairs are pipelined. Shard A
(d36e9e24, Spec.lean target notes) wrote that "start is acknowledged only at completion (gcd_rig.v's header; not
proved here), so the target would not hold two pairs".

## 1. When are the inputs acknowledged? (audit/t2/mon_t2.v, bq1_target_v6_max_monitor.log)
Unmodified target, vector 6, SLOW_MAX: a_ack rises 0.799 us, start_ack 0.909 us, in_ack 0.909 us, and all three fall
by 0.988 us. out0_req rises only at 9.987 us. Same pattern on laps 2 and 3. So the input handshake completes about
9 us BEFORE the result. gcd_rig.v:291-294 ("The kernel acknowledges `start` only when it is finished ... the SAME
instant") is FALSE for the real circuit, and so is Spec.lean's target note built on it. Shard C's model (inputs
acknowledged early) is right.

## 2. Replay (audit/t2/env_t2.v, replay_pipe1.log, replay_pipe0.log)
env_t2 replaces the rig's env node, exactly what Spec.lean's `circuit N B` does ("their drivers in the bitstream
(the rig's) are removed"). It forces n7234 (request) and the operand nets with a four-phase handshake on in_ack, and
acknowledges out0 by forcing n5852, sampling rig_res_data 3 ns after each out0_req rise (out0_req leads its data
by ~152 ps). Data is held from 2 ns before each request rise until the acknowledge falls. Pairs: (a,b) =
vector 6 (0x798F20, 0x12B87CA0; gcd 0x20; both even, deep k-loop), then vector 4 (1, 1; gcd 1; odd). Both are
table entries, so the target's merged-bit wiring represents them.
- PIPE=1 (pair 2 offered as soon as pair 1's input handshake completes; THE goal's pipelined environment):
  pair 1 accepted 2.311 us, pair 2 accepted 2.894 us; **out0 #1 = 0x00000001 at 3.011 us, out0 #2 = 0x00000020 at
  11.346 us.** The k-th output is NOT the gcd of the k-th pair: REORDERED. Both values are correct; the order is wrong.
- PIPE=0 (control, sequential): out0 #1 = 0x20 at 11.313 us, then pair 2, out0 #2 = 1 at 12.014 us. In order.

## Verdict
- Shard C's reordering counterexample: CONFIRMED on the target's own configuration (fid GLS, one corner, one pair
  ordering). The margin is ~8 us, far larger than any band effect.
- THE goal's theorem as specified (Spec.lean `Correct`: out0's k-th request carries gcd of the k-th pair, for every
  H_ENV environment, which allows offering pair k+1 right after pair k's input handshake): FALSE for the target
  bitstream. This trace satisfies the drafted H_ENV (four-phase on the shared request, data held su = 2 ns before the
  request, out0 acknowledged >= 3 ns after its request).
- gcd_rig.v's "start acknowledged only when finished" and Spec.lean's "the target would not hold two pairs":
  REFUTED by the GLS.
- Not checked: deadlock (C's second claim), other corners, other pairs. The rig's own env is two-stage and waits
  for each result, so the board as built never pipelines. The failure needs an environment that THE goal allows
  and the board's rig does not provide.
